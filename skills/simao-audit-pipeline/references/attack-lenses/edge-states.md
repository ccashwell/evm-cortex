# Lens 11 — Edge & Terminal States

You own the states the developers never tested: empty, single, first, last, zero, maximum, expired, paused, ended, and cancelled.

Code is written for the steady state — many users, non-zero balances, an ongoing period. Almost every function has at least one boundary where its assumptions quietly stop holding, and the terminal states (expiry, vault ended, program finished, last user) are where the accounting bugs concentrate because nobody re-derives the math for them.

## The checklist — run every one against every stateful function

**Zero / empty.** `totalSupply == 0`, no depositors, no stakers, zero rewards, zero amount, empty array. What does the division do? Where do distributed tokens go when there is nobody to receive them?
> *Lost rewards when the supply is 0, which always happens if rewards are queued before anyone has StakeTracker tokens*
> *Having no deposits in `StakedEXA` will lead to stuck rewards when harvesting*
> *Utilization rates are 0 when average assets are 0, which may be used to game maturity borrows / deposits / withdrawals*
> *Unconditional lastUpdated advance in RangePool.sync leads to loss of streamed BMX when pool liquidity == 0*

**One / sole occupant.** A single participant, one wei, one share, the only LP. Strict `<` guards frequently exclude the legitimate sole-occupant case; verify `<=` is the right comparator on every count check.
> *A malicious user may unlock instantly all the funds from the `FluidLocker` when no one is staking in the Tax pool*
> *`ClearingHouseLiq::_finalizeSubaccount()` does not check if the subaccount has lps*
> *Unassigned pool earnings can be stolen when a maturity borrow is liquidated by depositing at maturity with 1 principal*

**First.** First depositor, first mint, pool creation, initialization. Who sets the initial rate and can it be set adversarially?
> *`BoldToken` initialization can be frontrun to silently mint/approve bold to an attacker*
> *Incorrect initial deposit calculation may cause cancelProgram to revert*

**Last.** The last withdrawer, the last share burned, the final unit of supply, the last bond. This is his highest-yield edge: run the full unwind and check whether the final actor is paid and whether residual value is trapped.
> *User to sell the last supply will make the exchange contribution forever stuck*
> *Interest generated by last bond will not go to anyone when liquidating as there is no bond amount to collect it*
> *`totalEarnings` is incorrect when withdrawing after ending which will withdraw too many funds leaving the `Vault` insolvent*
> *Liquidator will leave a pool with unassigned earnings on `Market::clearBadDebt()` free to claim for anyone when the repaid maturity is not the last*

**Expired / matured / ended.** Every function behaves differently after expiry, and the expiry-path variants are the least reviewed code in any protocol. Re-run the whole lifecycle past the boundary.
> *Users redeeming early will withdraw `Ra` without decreasing the amount locked, which will lead to stolen funds when withdrawing after expiry*
> *Withdrawing all `lv` before expiry will lead to lost funds in the Vault*
> *Expired maturities longer than `FixedLib.INTERVAL` with unaccrued earnings may be arbitraged and/or might lead to significant bad debt creation*
> *`LidoVault::vaultEndedWithdraw` doesn't take into consideration income withdrawals before slashing, blocking variable users from withdrawing their income*
> *`VaultPoolLib::reserve()` will store the `Pa` not attributed to user withdrawals incorrectly and leave it untracked once it expires again*

**Paused / frozen / halted.** Which functions must remain available while paused (repay, liquidate, withdraw)? Can the pause be applied as documented? What happens to in-flight requests?
> *Cannot repay or liquidate on paused asset*
> *Admin will not be able to only pause deposits in the `Vault` due to incorrect check leading to DoSed withdrawals*

**Cancelled / reverted / retried.** Cancellation and retry paths must fully undo what the forward path did. They usually undo most of it.
> *Cancelling rounds after finalizing will lead to incorrect `globalTokenAllocPerIDORound` tracking*
> *Method refundPlayers doesn't update `_lockedETH` in WinnableTicketManager*
> *`DrawManager.canStartDraw` does not consider retried RNG requests when determining if a new draw auction can be started*

**Maximum / saturation / cap.** Full utilization, cap reached, maximum leverage, maximum array length, ratio at exactly 1. Down-casts wrap near saturation, and caps interact badly with pro-rata math.
> *Market utilization ratio near 100% will DoS deposits as harvest tries to withdraw and reverts*
> *Funding cap in `IDOPoolAbstract::_basicParticipationCheck()` is imprecise and can lead to excessive tokens sold*
> *DoSed liquidations as `PrizeVault::liquidatableBalanceOf()` does not take into account the `mintLimit` when the token out is the asset*
> *Yield loss due to `StrategyRouterLib::rebalanceStrategies()` not allocating saturated strategy deposits*

**Threshold boundaries.** Any comparison against a configured threshold: test exactly at, one below, and one above. Value that falls on the wrong side of a threshold often silently changes owner.
> *In `PCLBaseSwapInside::_compoundRewards()`, if the sellPortion is smaller than rewardSwapThreshold, some of the rewards will move to keepPortion*
> *`ManagedLeveragedVault::decreaseLeverage()` will not work when it goes below the minimum debt*
> *Protocol will need to donate minimum debt for all new ManagedLeveragedVaults*

**Reconfiguration mid-flight.** A parameter changed while positions are open: epoch duration, market address, reward duration, provider, multiplier ordering.
> *Changing the epoch duration will completely break the vault and the slashers*
> *`MultiplierContract::proposeMultipleUpdates()` updates `maxLevel` before executing the update*
> *Rewards can disappear when new rewards are distributed in the RewardsController*
> *Vesting interest is not reset to 0 in case there is no interest in `LoopedVault11::updateTotalAssets()`*

## Method

Do not scan for these opportunistically. Take each stateful function from the money map and walk the full checklist against it. The value of this lens comes from being exhaustive, not clever.

## Every finding needs the exact state

Name the precise boundary value and how it is reached, then the resulting behavior versus the intended behavior.
